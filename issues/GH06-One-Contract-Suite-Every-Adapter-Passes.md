# GH06 — One Contract Suite Every Adapter Passes

**Status:** Implementing, for sprint 3; blocked by `porelo` [B253](https://github.com/porelo-ai/porelo/blob/main/issues/base/README.md#b253).
**Size:** L - a new published module with a suite and its recordings, the adapter on the second contract, its
packages renamed, and the rename's round across this repository and three others.

**What must be true.** This repository builds the module `porelo-build-contract`, a suite that drives an adapter
over `org.fuin.porelo.Build2` from recorded answers and holds every case the build contract names, and the `github`
adapter passes it as `porelo-adapter-github`, packaged in place of `porelo-build-github` at
`/usr/libexec/porelo/builds/github`; an adapter changed to answer one case wrongly fails the suite.

## Why

From porelo-project [PJ62](https://github.com/porelo-ai/porelo-project/blob/main/issues/README.md#pj62): every forge
adapter lives in one repository beside one suite, so a second adapter is held to what the first answers. The suite
is published, so an adapter outside the project can run it.

## Plan

Read in `pom.xml`, `reader/` (`GitHubReader`, `Http`, their tests, `src/deb`), `.github/workflows/build.yml` and, in
`porelo`, `builds/api` on the second contract (`InstalledBuildReader`, `BuildMain`, `Build`, `BuildRefused`).

1. **The layout after the rename.** The root becomes `org.fuin.porelo:porelo-adapters` (pom, parent `porelo-parent`,
   SCM and issue URLs on `porelo-adapters`); its parts: `contract` (`porelo-build-contract`, jar) and a grouping
   module `adapters` (pom) holding `github` (`porelo-adapter-github`, today's `reader`, moved with `git mv`). The
   Java package `org.fuin.porelo.build.github` stays: it names what the code reads, and the executable's name and
   forge identity `github` are unchanged. `porelo.version` follows `porelo`'s snapshot with `Build2` until a release.
2. **The suite, `porelo-build-contract`.** An abstract JUnit 5 class `AdapterContract` an adapter's test extends,
   naming its main class and its recordings' directory; one `@TestFactory` yields a test per case. Each case starts
   the adapter as Porelo does - an executable that runs its main on the test class path, through
   `InstalledBuildReader` over its socket, the launcher `InstalledBuildReaderTest` uses made public here as
   `JavaExecutable` - with `Target.api` pointed at a loopback forge double (`com.sun.net.httpserver`) serving the
   case's recordings, and compares the answer with the case's expectation, which the suite holds and no adapter can
   change. A request the recording lacks is answered 404 and fails the case naming the request.
3. **The cases**, each a record of a question (`head` or `build` with its logs) and an expected answer or refusal:
   a branch's head; an absent branch; a commit with no build; queued; running; passed; failed (the failed job's log
   only); cancelled; logs `none` (jobs, no log, no log request made), `failure`, `all`; a log over 64 KiB keeps its
   end; more than 50 jobs keep the failed ones; logs over 2 MiB shared; `RateLimited` with its retry-after,
   `CredentialRefused`, `NoSuchRepository`, `Unreachable` (the double closes the connection). **Two guards of
   harm:** every API request carries the case's token, and no request after a redirect to another host does.
4. **Recordings**: one directory per case, one JSON file per exchange (method, path and query, status, headers, a
   body or a body file); large bodies are generated by the suite from a size, so nothing of 2 MiB is committed.
   The `github` ones are recorded once from GitHub - a public repository's runs, one green and one red - and
   reduced to what the adapter reads; today's inline JSON in `GitHubReaderTest` is not a recording.
   **Decided:** they are recorded once from the Ubuntu VM, with the CI's read token copied into `core` for that run
   only and removed right after; the recordings hold no token.
5. **The `github` adapter on `Build2`**: `look` becomes `build`; `none` lists the jobs and requests no log;
   `GitHubContractTest extends AdapterContract`. `GitHubReaderTest` keeps only what the suite does not name
   (address forms, dot segments, pagination past 1,000 runs, the second page failing).
6. **Packages**: `porelo-adapter-github` (`.deb` `Replaces:` and `Conflicts: porelo-build-github`; `.rpm`
   `Obsoletes: porelo-build-github`), at `/usr/libexec/porelo/builds/github`; `build.yml` builds, smoke-tests
   (`describe` says `github`, version 2) and publishes it under `p/porelo-adapter-github/`, and its index check.
7. **Publishing `porelo-build-contract`** to Central: it opts in, the root declares `flatten-maven-plugin`;
   `porelo-adapter-github` stays off Central (Artifactory only).
8. **The rename's round** (39 occurrences in 14 files, `command grep -rn porelo-build-github`): POMs, workflow,
   `README.md`, `CONTRIBUTING.md`, `doc/index.md`, the issue index, `AGENTS.md` ("Porelo Build GitHub" →
   "Porelo Adapters"), `mkdocs.yml`; released changelogs stay. Outside this repository, asked of their owners in
   the channel: `porelo`'s `doc/running.md` package name, the site's link, porelo-project's `project.yml` upstream.

**Red first:** `GitHubContractTest` on today's adapter: it speaks `Build1`, so every case is refused at the handshake.
Then each case is seen red once with the adapter broken for it (a mapping changed, a header dropped).

The contract replay uses reduced captures of `porelo-ai/porelo-frontend`: the failed and passed runs each
have nine jobs, and the failed Windows job's log arrives through a 302 to a blob host without authorization.
The real head, missing branch, empty run list, 401, and ref 404 are also replayed. The uncaptured repository
confirmation after the ref 404 and the green jobs' log downloads are explicitly generated. Queued, running,
cancelled, both rate limits, transport failure, and size boundaries are generated from the real reduced
shapes; the captures do not establish what a just-pushed queued commit returns. The cases and their
provenance are specified in [the contract documentation](../doc/contract.md).

The failed-job capture contains no match for the four checked credential markers. Its retained replay body
has 69,632 bytes, preserving a 4 KiB prefix before the expected 64 KiB tail, whose digest is fixed in the
suite independently of the replay files. Generated matrix lists use bounded counts; repeated redirect/blob
exchanges keep all fifty log downloads mandatory with three files for the shared-budget case.

## Acceptance

- The suite runs every case of *Plan* step 3 against `porelo-adapter-github` from recordings, with no network; each
  case is seen to fail once with the adapter broken for it, and a request the recording lacks fails naming it.
- On the Ubuntu VM, `porelo-adapter-github` installed over `porelo-build-github` removes it, keeps the executable's
  path, and `porelo build status` reads a red and a green Build of a GitHub repository.
- `porelo-build-contract` is in Central's index at the released version.
